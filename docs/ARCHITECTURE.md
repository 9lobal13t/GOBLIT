# Архитектура GOBLIT

Документ описывает то, что **реально реализовано**. Запланированные части помечены и ведут в [ROADMAP.md](ROADMAP.md).

## Главные принципы

1. **Решает сервер.** Здоровье, урон, награды, профиль, настройки и состояние мира хранит и меняет только сервер. Клиент отвечает за ввод, интерфейс, локальные эффекты и отправку *намерений*.
2. **Каждый запрос клиента недоверенный.** Все аргументы приходят как `unknown` и проверяются: тип, длина, диапазон, право на действие, расстояние, частота.
3. **Данные отдельно от кода.** Числа баланса лежат в `Config`, содержимое — в `Definitions`, логика — в сервисах.
4. **Чистая логика тестируется без Studio.** Модули в `shared/Logic` не используют Roblox API и не делают `require` других модулей: зависимости передаются параметрами. Поэтому их запускает Lune.
5. **Никаких пустых заготовок.** Файл появляется вместе с работающей системой.

## Запуск

Сервер (`src/server/init.server.luau`) и клиент (`src/client/init.client.luau`) стартуют одинаково:

1. *(только сервер)* `NetServer.init()` создаёт сетевые события из реестра.
2. `init()` всех модулей по порядку: подготовка и **подписки на сигналы других модулей**.
3. `start()` всех модулей: игроки, циклы, обработка событий.

Подписки делаются в `init`, потому что любой `start` может сразу сгенерировать событие. Например, если DataStore недоступен, профиль «загружается» мгновенно, и `ProfileLoaded` срабатывает внутри `PlayerDataService.start`.

Каждый шаг обёрнут в `ErrorReporter.try`: ошибка одного модуля попадает в лог и не останавливает запуск остальных.

## Сетевой слой

```
shared/Net/Remotes.luau     реестр: имя, направление, надёжность, лимит частоты, формат аргументов
server/Net/NetServer.luau   создаёт события, лимитирует частоту, изолирует ошибки, учитывает нарушения
server/Net/Guard.luau       проверка аргументов от клиента
shared/Net/NetClient.luau   клиентский доступ к событиям
```

- Универсального события «выполни команду» нет. Каждое событие отвечает за одно действие.
- Лимит частоты работает как token bucket на игрока и событие. Превышение отклоняется до вызова обработчика.
- Нарушения не наказываются автоматически (ТЗ 25): запрос отклоняется, ведётся счётчик, а лог пишется не чаще раза в 30 с на игрока. Задержка сети или двойной клик не должны приводить к бану.
- Для частых косметических событий в реестре есть флаг `unreliable` (будет `UnreliableRemoteEvent`). Сейчас все события надёжные.

| Событие | Направление | Аргументы | Лимит |
|---|---|---|---|
| `UpdateSetting` | клиент → сервер | `key: string ≤ 32`, `value: boolean \| number` | 5 подряд, 2/с |
| `Attack` | клиент → сервер | `direction: Vector3` (куда бьём; всё остальное решает сервер) | 6 подряд, 4/с |
| `Notify` | сервер → клиент | `{ text: string, kind: "info" \| "success" \| "warning" \| "error" }` | — |
| `Hit` | сервер → клиент | `{ position: Vector3, amount: number, crit: boolean }`, ненадёжное | — |
| `AttackPerformed` | сервер → клиент | `interval: number` — сервер принял удар, пошла перезарядка | — |

Взаимодействие с объектами мира идёт через `ProximityPrompt`: он из коробки работает с клавиатурой, геймпадом и сенсорным экраном. Срабатывание подсказки сервер тоже не принимает на веру: проверяет дистанцию до объекта и частоту.

## Репликация состояния

Состояние, которое нужно интерфейсу, сервер выставляет **атрибутами игрока** (имена в `Constants.PlayerAttr`): здоровье, выносливость, уровень, зона, валюты, `DataReady`, `SaveDisabled`. Атрибуты реплицируются автоматически и видны всем клиентам, что пригодится для панели группы. HUD только отображает эти значения и ничего не считает сам.

Настройки реплицируются своему игроку атрибутами `Setting_<ключ>`. Клиент показывает только значение, подтверждённое сервером.

## Профиль игрока (`PlayerDataService`)

Схема, миграции и проверка данных находятся в `shared/Logic/ProfileSchema.luau` (чистый модуль, покрыт тестами).

Хранение: ключ `profile_<UserId>` в DataStore `Config.Data.StoreName`. Запись имеет вид `{ Data = профиль, Lock = { JobId, Session, Time } }`.

В Studio используется отдельное хранилище `StoreName .. StudioStoreSuffix` (`GOBLIT_Profiles_v1_Studio`). Studio с доступом к API работает с теми же хранилищами, что и живая игра, а тесты не должны трогать настоящие профили или отбирать их у живого сервера. Имя хранилища печатается в Output при старте сервера.

Протокол блокировки сессии:

Решения о блокировке принимает чистый модуль `Logic/SessionLock` (покрыт тестами). У каждой сессии игрока свой идентификатор (`Session`, GUID).

1. **Загрузка** выполняется через `UpdateAsync`. Если блокировки нет или она осталась от этого же сервера, профиль забирается сразу. Устаревшая блокировка (старше `LockTtlSeconds`) тоже забирается сразу. Свежую чужую блокировку сервис ждёт `ForceLockAfterSeconds` (30 с) и только потом забирает: к этому времени финальная запись прошлого сервера гарантированно закончилась. Каждый захват устаревшей или чужой блокировки пишется в лог. Ошибки DataStore считаются отдельно: после `LoadAttempts` ошибок подряд игрок получает профиль без сохранения.
2. **Сохранение** тоже выполняется через `UpdateAsync` и пишет, только если в записи блокировка **этой** сессии. Чужая или пустая блокировка значит, что профиль уже забрали или отпустили. Тогда сессия прекращает сохранять, чтобы не затереть более свежие данные.
3. **Автосохранение** раз в `AutosaveSeconds` продлевает блокировку. Тест проверяет, что `AutosaveSeconds × 2 < LockTtlSeconds`.
4. **Выход игрока и `BindToClose`** записывают профиль и снимают блокировку. Перед этим вызываются хуки выгрузки: позже через них будут начисляться итоги прерванной экспедиции. Хук получает профиль и меняет его **напрямую**: `update()` внутри хука уже не работает. Перед записью профиль проходит схему. Когда в фазе 2 появится первый хук, этот контракт стоит заменить на передачу функции изменения с правилами `update()`.
5. Записи одного профиля не перекрываются. При быстром перезаходе на тот же сервер загрузка ждёт, пока завершится выгрузка того же `UserId`.

Защита данных:

- `update(player, mutator)` работает атомарно: мутатор получает копию, и при ошибке изменения отбрасываются. После изменения профиль снова проходит схему, так что, например, валюта не уйдёт в минус.
- Данные, записанные **более новой** версией игры, только читаются. Сохранение отключается, чтобы не потерять неизвестные поля.
- Если DataStore недоступен (Studio без доступа к API, неопубликованное место), игрок получает профиль по умолчанию и сохранение отключается. Игрок видит уведомление, а в HUD остаётся предупреждение. Профиль по умолчанию никогда не записывается поверх настоящего.

## Обработка ошибок

`shared/Util/ErrorReporter.luau`:

- `try(context, fn, ...)` выполняет функцию в защищённом режиме и пишет ошибку в лог со стеком;
- одинаковые сообщения подавляются на 10 с, а затем выводятся с числом скрытых повторов;
- в логи не пишутся персональные данные, только `UserId`.

Через `try` вызываются обработчики сетевых событий, сигналов и шаги запуска.

### Интерфейс на телефонах

Правила выведены из проверки на iPhone 7:

- При сенсорном вводе интерфейс не уменьшается ниже макета 1280×720. Итоговый масштаб не ниже 0,8, поэтому мелкий текст (14) не бывает меньше ~11 точек.
- Любая кнопка не ниже `Theme.TouchTarget` (44 точки).
- Длинные списки (панель настроек) прокручиваются, если не помещаются по высоте.
- Число одновременных уведомлений зависит от высоты экрана, чтобы они не заходили на полосу здоровья.
- У кнопок, цвет которых меняет код, `AutoButtonColor = false`.
- Область прокрутки (`CanvasSize`) задаётся кодом, а не через `AutomaticCanvasSize`: под `UIScale` он считает её неверно.
- Стандартные элементы Roblox не перекрываются. Левый верхний угол оставлен для чата на ПК. Полоса здоровья на сенсорных экранах сужается до промежутка между джойстиком и кнопкой прыжка.

## Бой

Удар проходит так:

1. Клиент отправляет `Attack` с **направлением** — и больше ничем.
2. `CombatService` проверяет: жив ли герой, есть ли персонаж, прошла ли перезарядка (с запасом `TimingTolerance` на сетевую задержку), и находит цели в секторе удара — по расстоянию, углу и разнице высот. Учитывается радиус цели, чтобы по крупному врагу не надо было целиться в центр.
3. Серия ударов подряд (в пределах `ComboResetSeconds`) усиливается по `ComboMultipliers`, а завершающий удар бьёт по более широкому сектору.
4. `DamageService` — единственное место, где бросается кубик крита и применяется урон. Формулу считает `Logic/Damage`, применяет `EnemyService.applyDamage`.
5. Клиенту уходит `Hit` для цифр урона. Здоровье врага клиент берёт из атрибутов его модели, которые ставит сервер.

Клиент не может ни ускорить удары, ни ударить издалека, ни назначить урон: он присылает только намерение.

## Как добавить…

- **Настройку:** добавьте запись в `ProfileSchema.SettingsSpec`. Панель, проверка на сервере и сохранение подхватят её автоматически. Добавляйте только настройку, которая уже на что-то влияет.
- **Сетевое событие:** опишите его в `Remotes.luau` с форматом аргументов и лимитом, а на сервере подключите через `NetServer.onServerEvent` и проверьте каждый аргумент.
- **Поле профиля:** добавьте поле в `ProfileSchema` и в `sanitize`. Если меняется смысл старых данных, повысьте `CURRENT_VERSION` и добавьте миграцию. Тест на неё обязателен.
